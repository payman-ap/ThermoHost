# 6. Enumeration, descriptors, and device identity

## What happens before your program opens the board

When a board attaches, the host must discover what it is and how to operate it.
Enumeration obtains descriptors, assigns an address, and configures the device.
Only after the relevant operating-system setup can your DLL discover a usable
device interface. The console does not perform the initial electrical attach
or invent the USB address.

Think of two separate conversations. The operating system asks, “What device
and interfaces are you?” Your application later asks, “Do you implement the
fresh-temperature protocol?” The first establishes transport access; the second
establishes application compatibility.

## The descriptor hierarchy in this project

The source of runtime identity is
[usb_descriptors.c](../../firmware/usb/usb_descriptors.c). The device descriptor
contains VID, PID, revision, string indices, and configuration count. The
configuration descriptor includes one interface and its two bulk endpoints.
String callbacks supply human-readable names and a serial number.

Microsoft's [device-descriptor guide](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-device-descriptors)
explains whole-device fields, while the
[configuration-descriptor guide](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-configuration-descriptors)
explains the configuration/interface/endpoint hierarchy. The following
interpretation applies those ideas to the actual local source.

```c
.bcdUSB = 0x0210,
.bDeviceClass = 0,
.bDeviceSubClass = 0,
.bDeviceProtocol = 0,
```

The USB revision field is not a temperature protocol version and does not make
the hardware high speed. A device class of zero delegates class information to
interfaces. The interface generated by `TUD_VENDOR_DESCRIPTOR` uses the vendor
class rather than CDC. This is why matching only the whole-device class could
mislead you.

## Different identifiers answer different questions

| Identifier | Current value or source | Question it answers |
| --- | --- | --- |
| VID/PID | `1209:0001` | Which product identity is advertised? |
| Device revision | `bcdDevice = 0x0101` | Which descriptor/device revision is advertised? |
| Product string | `ThermoHost thermometer` | What name can a person see? |
| Serial string | SDK unique-board-ID helper | Which individual flash-backed identity is exposed? |
| Interface GUID | `D026972A-922E-455F-A035-B08D3E383FE4` | Which Windows interface family should the DLL enumerate? |
| Capability reply | `TH`, 2, 20, 32 | Does this device support the required command/response contract? |

The source labels the VID/PID as private-test identifiers rather than universally
unique project allocations. Preserve that context when reading captures. The
DLL does not presently select by serial number or enumerate all matching
devices; it attempts the first matching present interface.

An RP2040 board is not its CPU alone. The SDK's unique-board-ID facility uses
flash identification on this platform. Do not infer that the code reads a
user-defined USB serial string from a special RP2040 serial register.

## TinyUSB macros build byte sequences

```c
TUD_CONFIG_DESCRIPTOR(
    1, 1, 0, THERMO_CONFIG_LENGTH, 0, 100),

TUD_VENDOR_DESCRIPTOR(
    0, 4, THERMO_EP_OUT, THERMO_EP_IN, CFG_TUD_VENDOR_EPSIZE)
```

The configuration is numbered 1, has one interface, and declares a power budget
through the macro's milliamps argument. The vendor interface is number 0 and
uses string index 4. The final argument sets endpoint packet size. These macros
emit descriptor bytes; they do not open a Windows connection or define your
temperature fields.

Index versus value is easy to confuse. The callback receives descriptor index
0 for the first configuration, while that configuration's selectable value is
1. The code rejects other indices rather than returning the first descriptor
for every request.

## String descriptors have their own encoding

String zero lists languages; here it advertises US English `0x0409`. Other
strings are returned in UTF-16 code units with a descriptor header. The code
copies ASCII characters into 16-bit slots, which works for the current names.
That loop is not a general UTF-8-to-UTF-16 converter.

The returned buffer is static. A callback must not return a pointer to a local
array whose lifetime ends immediately. TinyUSB needs the data after the C
function returns. The 32-word allocation reserves one word for the header and
up to 31 characters. Header length is measured in bytes, so it uses
`2 * count + 2`, not just `count`.

## Why a correct descriptor is a protocol commitment

If the descriptor promises a 64-byte bulk endpoint and a vendor interface,
TinyUSB's configuration and the host's expectations must agree. A malformed
length can prevent enumeration before any temperature request exists. That is
why the Microsoft-descriptor source uses compile-time size checks.

Names are comparatively cosmetic. Endpoint types, class codes, lengths, and
binding properties affect behavior. During debugging, record the actual
descriptors observed by the host rather than assuming the intended source was
the image most recently flashed.

## Cached identity and firmware replacement

Both vendor firmware targets share the same USB descriptors. Consequently,
switching from probe to live firmware need not create a visibly different
product name in Device Manager. The application capability query is the
reliable discriminator in this design.

Windows can retain device information between connections. A source edit alone
does not prove the host has reevaluated all properties, nor that a build was
flashed. Diagnose from the connected device's observable properties and the
capability response. Avoid changing VID/PID or GUID randomly to make a symptom
disappear; that can hide a descriptor defect and break matching clients.
