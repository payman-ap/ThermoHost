# 3. Hardware and the meaning of a measurement

## Separate sensing, conversion, and transport

The thermocouple is the sensing element. The MAX6675 is the converter. The
RP2040 is the processor that coordinates communication. USB transports results
to the PC. Replacing the USB protocol would not improve the thermocouple's
physical response, and replacing the DLL would not change the converter's
quantization.

A thermocouple produces a small voltage associated with the temperature
difference between junctions. Interpreting it requires a reference-junction
estimate. The MAX6675 performs cold-junction compensation and exposes a
read-only SPI-compatible result. Its specified resolution is 0.25 degrees C,
and its conversion time is up to 0.22 seconds under the datasheet conditions.
The project allows 0.25 seconds. These electrical facts come from the
[MAX6675 datasheet](https://www.analog.com/media/en/technical-documentation/data-sheets/max6675.pdf).

The extra 30 ms is conversion margin, not a USB requirement. A much faster
serial clock would not remove the converter's wait. This is your first example
of a system bottleneck being somewhere other than its communication link.

## Wiring in this repository

| Signal | RP2040-Zero connection | Role |
| --- | --- | --- |
| MAX6675 VCC | 3V3 | Supply used by this project. |
| MAX6675 GND | GND | Common reference. |
| MAX6675 SO | GP0 | Sensor serial output to SPI0 input. |
| MAX6675 CS | GP1 | Software-controlled sensor selection. |
| MAX6675 SCK | GP2 | Clock generated by SPI0. |

GP numbers are GPIO identifiers, not arbitrary physical connector pin numbers.
Match the board labels and orientation. Change wiring with USB disconnected,
then check that the supply and ground are correct before reconnecting. This
course assumes this existing low-voltage sensor setup; a bare chip's electrical
specification is not proof that every breakout module has identical circuitry.

There is no MOSI command wire to the MAX6675 in this circuit. It is a read-only
device. The SPI controller still needs outgoing dummy bits to generate clock
pulses, but the sensor has no MOSI input to consume them.

## The RP2040's job

The RP2040 contains CPU cores and peripherals, including SPI and a USB
controller. A peripheral is specialized hardware that performs operations
without the CPU manually toggling every bit. Your firmware configures SPI0,
then asks it to receive two bytes. TinyUSB configures the USB controller and
provides endpoint-level services. The application uses one main execution
loop; it does not distribute this design across both cores.

The board's external flash stores the firmware image. The boot process starts
that firmware after reset. SRAM holds variables and buffers while the program
runs. These are distinct from the MAX6675's conversion state and from Windows
process memory. A token crosses USB as copied bytes, not as a pointer into
either processor's memory.

For hardware-level expansion, consult the official
[RP2040 datasheet](https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf),
especially GPIO function selection, SPI, USB, and boot behavior. This booklet
does not reproduce the register manual; it follows the SDK operations actually
used by the project.

## Resolution, accuracy, repeatability, and response

Suppose repeated readings are 25.00, 25.00, and 25.25. The 0.25 step is
resolution. Whether the true junction is 25.10 or 27.00 is an accuracy question.
Whether repeated measurements under unchanged conditions agree is a
repeatability question. How quickly a probe follows a changing surface is a
physical response question. None can be established merely by printing more
decimal places.

The converter's open-thermocouple detection is another limited observation. A
fault bit identifies a particular condition detected by that circuit. A zero
fault bit does not prove good calibration, correct probe placement, correct
polarity, or an undamaged cable. The current application reports the provided
fault; it does not implement a general measurement-health model.

This matters when designing a control loop. A plausible but inaccurate
temperature may be more dangerous to the control algorithm than a clearly
reported transport timeout. Data validity has more dimensions than “the USB
read returned bytes.”

## What is the sample time?

The firmware timestamps after reading the sensor. That timestamp is the
RP2040's uptime near acquisition readout. It is not the exact instant of a
thermocouple voltage sample, not Windows wall time, and not the moment the
console displays the number.

The conversion occupies an interval. The probe itself also has thermal lag.
For a slow thermometer, recording readout time is often adequate. For
synchronized acquisition, you would first define whether your timestamp means
conversion start, midpoint, end, or data publication. You would then measure
and document the uncertainty. The current DLL discards the timestamp from its
public result, so a client cannot reconstruct that timing precisely.

## A useful diagnostic order

Start by verifying sensor output with `firmware.uf2` and a serial terminal.
Then use the USB probe with the matching historical host code to isolate USB.
Finally use `thermometer_usb.uf2` and the current host together. This is the
reason the repository keeps three firmware applications rather than only the
final one: each removes variables from an investigation.

A serial-terminal success establishes that some sensor and SPI operations
work. It does not establish that the vendor interface, WinUSB binding, or
fresh-response decoder works. Conversely, fixed 42.25-degree USB packets prove
no physical temperature acquisition. Evidence should be stated at the layer
where it was collected.
